# License Data Quality Pipeline and Early Alerts

[![CI](https://github.com/reginaldooo/license-compliance-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/reginaldooo/license-compliance-pipeline/actions/workflows/ci.yml)

> **All data in this repository is synthetic.** The company, contracts, owners, and usage are generated by a seeded script. Nothing here comes from a real organisation, and no employer branding is used.

A Python pipeline that ingests messy software-license spreadsheets, normalizes product names, checks data quality, raises renewal and compliance alerts, measures its own precision and recall on injected anomalies, and sends a daily digest for two sites (Paris and Jakarta).

See [docs/EVIDENCE.md](docs/EVIDENCE.md) for proof of scheduled runs, with its limits.

## Pipeline

```
generate -> ingest -> normalize -> data quality checks -> alert rules -> curated tables -> digest
```

## Quick start

```bash
uv sync
uv run ruff check .
uv run pytest
```

## Assumptions register

Every parameter lives in `src/license_pipeline/config.py`.

| Parameter | Value | Basis |
|---|---|---|
| Random seed | 42 | Reproducible runs |
| Reference date (`TODAY`) | 2026-11-18 | Fixed so tests and evaluation are deterministic |
| Sites | Paris (Europe/Paris), Jakarta (Asia/Jakarta) | Two-site team |
| Contracts | 120 | Enough rows for meaningful rule statistics |
| Owners | 25 | Synthetic |
| Usage seats | 1500 | Synthetic |
| AI seats | 200 | Synthetic |
| Share of unused seats | 37% | Published SAM research reports about 36 to 38% unused seats |
| Unused threshold | 90 days without activity | Alert rule definition |
| Renewal windows | 30, 60, 90 days | Alert rule definition, combined with `notice_days` |
| Usage spike | Modified z-score above 3.5 on median and MAD, MAD floor of 1 percentage point | An IQR fence missed every spike once a third of the pairs spiked, because the spikes raised the fence. Median-based statistics tolerate up to half |
| Price change | Microsoft after 2026-07-01 | Assumed vendor price change for the rule |
| Fuzzy match min score | 88, at least 6 characters, ties within 2 points are ambiguous |  rapidfuzz WRatio. Mapped every case, typo, and suffix variant and no unrelated name when tuned on the generator's noise |
| Injected anomalies | 8 per alert rule | Ground truth for precision and recall |
| Unit costs | Rounded list-price estimates | Illustrative only, not real quotes |
| Product names | Raw names carry typos, case, and vendor prefixes | Mimics spreadsheet inventory |
| Dates | Mixed formats (ISO, DD/MM/YYYY, "12 Mar 2026") | Mimics spreadsheet entry |

## Synthetic data and ground truth

`uv run python -m license_pipeline.generate` writes raw CSVs to `data/raw/` (git-ignored, regenerated from the seed). The generator also writes `ground_truth.csv`, which lists every injected case per rule. Only the evaluation step reads it; the pipeline never does.

| Injected case | Count | Rule |
|---|---|---|
| Contract near renewal (30, 60, 90 day tiers, measured from the notice deadline) | 8 per tier | renewal_30, renewal_60, renewal_90 |
| Microsoft contract started before 2026-07-01 and renewing after it | 8 | price_change_renewal |
| Installs above entitlement per product and site, latest scan | 8 | installs_over_entitlement |
| Installs jump of 100% or more versus previous scan | 8 | usage_spike |
| Seat inactive for more than 90 days | about 37% of seats | seat_unused_90d |
| Duplicate, missing owner, invalid date, negative seats, unmapped product | 8 each | data quality |
| Contract without inventory, inventory without contract | structural, from 4 reserved product-site pairs each | data quality |

Rows that fail a blocking data quality check are quarantined and excluded from alert evaluation.

## Alert rules

| Rule | Definition |
|---|---|
| renewal_30 / 60 / 90 | Days until the notice deadline (renewal date minus notice days) is within 30, 60, or 90 days. A passed deadline falls in the 30 tier with high severity |
| installs_over_entitlement | Latest scan installs per product and site exceed seats purchased by valid contracts of owners at that site |
| seat_unused_90d | Usage or AI seat with no activity for more than 90 days |
| usage_spike | Month-over-month install growth per product and site above median + 3.5 x MAD / 0.6745 across all pairs (robust to many spikes) |
| price_change_renewal | Contract signed before a vendor price change date and renewing on or after it |

## Evaluation

`uv run python -m license_pipeline.evaluate` regenerates the data, runs the pipeline, and writes `reports/eval_report.md` with precision and recall per rule. On seed 42 and on 30 other seeds every rule recovered all injected cases with no false alarms. Injected cases sit well clear of every threshold, so this shows the rules match their definitions. It is not an accuracy claim for real data.

## Running the pipeline

```bash
# local only: writes Parquet to data/curated/ and a run log row
uv run python -m license_pipeline.run --local --generate

# with BigQuery (needs credentials, see below)
export GCP_PROJECT=your-project-id
export BQ_DATASET=license_compliance      # optional, this is the default
export GOOGLE_APPLICATION_CREDENTIALS=/path/to/service-account.json
uv run python -m license_pipeline.run --generate
```

| Table | BigQuery load mode | Why |
|---|---|---|
| dim_product, dim_owner, fact_*, dq_issue, alert | Replace each run | The dashboard reads the current state. Rows carry the `run_id` that produced them |
| pipeline_run_log | Append | Keeps one row per run: row counts, issue count, status, and the error text on failure |

A failed run writes a `failed` row to the local run log and re-raises, so a scheduled job turns red instead of passing silently.

## Daily digest

`uv run python -m license_pipeline.run --generate --today 2026-11-18 --digest paris --dry-run --force` prints the Paris digest without sending it. Alerts are filtered per site: contract alerts by owner site, installs and spike alerts by their `product|site` reference. Idle-seat counts are org-wide because seats carry no site.

| Setting | Where | Purpose |
|---|---|---|
| `SMTP_USER`, `SMTP_APP_PASSWORD` | GitHub secrets | Gmail account and app password (2-step verification required) |
| `DIGEST_TO` or `DIGEST_TO_PARIS` / `DIGEST_TO_JAKARTA` | GitHub secrets | Comma-separated recipients |
| `GCP_PROJECT`, `GCP_SA_KEY` | GitHub secrets | BigQuery project and service account key |
| `DASHBOARD_URL` | GitHub variable | Link added to the email once the dashboard exists. Omitted when unset |

Schedules (`.github/workflows/daily-digest.yml`), Monday to Friday:

| Site | UTC cron | Local time |
|---|---|---|
| Jakarta | `0 2 * * 1-5` | 09:00 WIB, no daylight saving time |
| Paris | `0 7 * * 1-5` and `0 8 * * 1-5` | 09:00 CEST in summer, 09:00 CET in winter |

GitHub cron only supports UTC, so both Paris hours are scheduled. The program checks the site's local clock first and exits before running the pipeline unless it is 09:00 there. A delayed GitHub start still sends if it lands within the same local hour. `workflow_dispatch` can send or dry-run either site on demand.

## Scenarios

Each run uses one data scenario. `--scenario random` picks one from the date, so a given date always gives the same scenario and a bad run can be reproduced. `--seed` changes the data inside a scenario. The daily workflow passes the date as the seed too, so the data differs every day.

| Scenario | What changes |
|---|---|
| baseline | Clean data, injected cases well clear of every threshold |
| borderline | Near-misses on both sides of every threshold: notice deadlines at 0, 30, 31, 60, 61, 90, 91, 92 days, installs at entitlement -1, 0, +1, seats idle 89 to 92 days, Microsoft contracts starting on and the day before the price-change date, and install growth from 12% to 80%. Labels follow the definitions in the alert rules table, written separately from the rule code |
| conflict | Contract ids that appear twice with different values (`conflicting_duplicate`), contracts whose renewal date has passed (`expired_contract`), and contracts whose owner id does not exist (`unknown_owner`). Conflicting copies are all quarantined, because there is no way to tell which one is right |
| messy | Harsher product names (spaces removed, hyphens, dropped or doubled letters, version suffixes, truncated cells), five date formats instead of three, blank seats, cost, or notice days, and three times as many unknown products |
| scale | Eight times the volume (960 contracts, 12,000 usage seats), more injected cases |

Every run records its scenario and its measured precision and recall (micro-averaged across rules) in `pipeline_run_log`, and prints a per-rule table on the GitHub Actions run page. What the scenarios found so far: borderline found no off-by-one errors in the rules (20 seeds). The scale scenario exposed that the first spike rule failed when many pairs spiked at once, which led to the median-based rule above. The messy scenario exposed two problems in product-name matching, over 20 seeds: 30 of 2,484 mappable names (1.2%) failed because the cell was cut off, and the fuzzy matcher mapped bare vendor names such as "Microsoft" to one arbitrary product. Both are fixed (unique-prefix matching for cut-off cells, and ties between products now stay unmapped). Name-match recall rose from 98.8% to 99.6%, with no wrong mappings. The nine remaining misses are all `MATLAB` with a letter dropped, which falls under the 6-character floor for fuzzy matching. That floor stays, because guessing at 5-letter fragments is how false mappings start.

Not covered: an owner sitting at the wrong site. Contracts carry no site of their own, so there is nothing for the owner's site to conflict with.
